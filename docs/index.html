An arena for testing AI security agents

Nidavellir provisions a reproducible target in a contained arena, gives a human or a bring-your-own agent a scoped research position over an MCP gateway, and independently verifies what actually happened. One engine serves two objectives: discovery — find and prove real vulnerabilities in real products — and evaluation — measure and compare the agents that hunt them.

How it works

One end-to-end loop, complete in the browser and running fully local: define the engagement, contain the target, research it, and score what the evidence supports.

01 / DEFINE

the engagement

Pick a purpose — benchmark, discovery, calibration, or manual research — then a challenge or an authorized target: a Git object, an OCI digest, a source bundle, or an imported Vulhub CVE environment. Purpose, participants, and the time box are recorded as immutable intent before anything runs.

Shipped
02 / PROVISION

a contained arena

Repo introspection and a deterministic-first build pipeline stand the service up, version-pinned. Nodes run on egress-locked segments proven by a containment test; generated infrastructure is never deployed unreviewed, and setup runs consent-gated with a hard privilege boundary.

Shipped
03 / RESEARCH

with an agent or by hand

A bring-your-own agent connects through the gateway as attacker, MITM, or defender — scope-enforced, budget-metered, key↔arena-bound, fully traced. Git change intelligence, hashed patch evidence, bounded file transfer, and a disposable headless browser are already there; an operator can drive the same arena with no model at all.

Shipped
04 / VERIFY

before anything is scored

A crash oracle turns crashes, sanitizer aborts, and unhandled 5xx into evidence. Deterministic validators confirm a finding — reflected XSS counts only when JavaScript is observed executing in a real browser. The operator verdict is authoritative, and the run exports as an Inspect-style score with an OpenInference-aligned trace.

Shipped

Two objectives, one engine

The same provisioning, containment, monitor, validator, and evidence machinery answers two different questions — and the answers feed each other.

Discovery

The target is under test

A vulnerability research platform: stand a real product up at an exact identity, contain it, work it from a stable position, and prove afterwards precisely what was hit. The output is a defensible record — finding, PoC, observed effect, affected identity, disclosure state — not a score. The participant, human or agent, is the instrument.

Evaluation

The agent is under test

An evaluation arena for complete agent builds — model, scaffold, tools, memory, policies, budgets together — run over held-out active challenges and compared on verified capability rather than claims. Nidavellir is the environment, capability boundary, observer, referee, and comparison layer; it never ships the agent it measures.

A challenge is a solved discovery problem with its truth withheld. Verified findings from real research are the only honest source of held-out evaluation material — public CTFs and known-CVE packs calibrate, but cannot settle a comparison participants may have trained on. That is why the platform is built to be useful to a researcher before it is built to rank an agent.

Three engine pillars

Both objectives stand on these three. Discovery and evaluation reuse the same arena, evidence, and scoring substrate — that is what lets a finding become a challenge without rework.

01 // Topologies & targets

Reproducible by identity

Provider-neutral scenarios describe arbitrary nodes and network segments, compiled by driver to docker-local containers today and to VM or cloud providers later. Targets resolve to immutable identities — a Git object, an OCI digest, a hashed source bundle, a pinned package — so a result names exactly what was tested.

02 // Participant runtime

Scoped, contained, traced

Humans and external agents enter through explicit stances — attacker, MITM, defender — with server-enforced key↔arena bindings, narrow capabilities, no egress by default, and an append-only trace. Containment is the primary control, not a setting the participant can talk its way past.

03 // Evidence & comparison

Proof outranks claims

Monitor signals, deterministic validators, content-addressed artifacts, and structured scores decide what a run achieved. Unknown is not refuted, discovery mode never pretends to know false negatives, and immutable identities plus replay are what make an agent-version comparison explainable instead of anecdotal.

System Architecture

A GUI-driven product on an API-backed architecture: the console presents and drives, while orchestration, persistence, validation, and scoring stay behind the service boundary.

Modular, decoupled subsystems

The console calls the orchestrator over REST and streams live arena state and audit events back over SSE. The orchestrator records every action to an append-only event spine and queues work through Redis to Celery workers, which drive the provider drivers that build and tear down arenas. External agents reach an arena only through the MCP gateway, which enforces stance capabilities, key↔arena bindings, and budgets. docker-local is the path whose full lifecycle is regularly live-verified; cloud and VM drivers remain deliberately deferred skeletons.

Who it's for

A bring-your-own-agent, contained, reproducible harness fits several kinds of work.

Teams building agents

A harness for your own agent

Test and regression-check the security agent you are building against targets you choose, with the model, scaffold, tools, and budgets recorded alongside the score — so a version comparison means something.

Enterprises

Evaluate agents on your code

Run an AI security agent against your own codebases in a contained arena, with a full audit trail. The platform ships no agent of its own, so the results stay yours.

Safety & eval researchers

Reproducible cyber evals

Cyber-offense evals on active challenges rather than static snapshots, with Inspect-style scores and traces in OpenTelemetry-GenAI and OpenInference shape, ready to flow into Langfuse, Phoenix, or Braintrust.

AppSec & red teams

Contained, scored pentests

Point an agent at internal or open-source software and let it work, safely boxed and scored. A human can drive any arena too, with no model in the loop.

Development roadmap

The engine and the console are shipped. What remains is the research runtime both objectives need, then the discovery lane that makes the platform useful to a researcher, and the workbench that turns single engagements into repeated, comparable evaluations.

Shipped · the engine and the product surface
Engine Shipped

Arenas, target intake, and the control plane

A FastAPI orchestrator over Redis/Celery workers and provider drivers, with an explicit arena state machine, an append-only event spine, TTL reaping, API-key roles, and encryption at rest. Scenarios describe arbitrary nodes and segments; targets resolve to immutable Git objects, digest-pinned OCI images, hashed source bundles, or named packages, and repo introspection stands a service up deterministically — falling back to verified Dockerfile synthesis that only returns an image that actually built.

Evidence Shipped

Monitoring, validators, scoring, and export

A crash oracle turns crashes, sanitizer aborts, unhandled 5xx, and resource exhaustion into deduplicated evidence, so a target with no known-CVE list is still scorable. Deterministic validators confirm findings — reflected XSS counts only when a platform-owned payload is observed executing in a real headless browser. Runs carry an Inspect-style structured score with milestone progress, reproducible PoCs, an operator confirm/refute path, and OpenInference-aligned trace and dataset rows.

Console C1–C4 Shipped

The GUI product model

Grouped navigation — Engagements, Evaluations, Library, Activity, Administration — with one unified engagement journey that carries purpose, source, participants, and an enforced time box into every launch path. The arena page became a contextual workspace whose live state streams over SSE, destroyed arenas became read-only records that keep their evidence, and Home plus the cross-engagement Findings and Evidence indexes are composed from the product objects themselves.

Next · the shared runtime, then the two lanes
R1–R3 Next

Research-ready runtime · shared prerequisite

The tools a serious offensive agent still needs, each arena-scoped and fail-closed: structured HTTP inspect, replay, and modify that accepts a node and a relative path rather than a caller-supplied URL; confined PoC execution in disposable, resource-capped containers with no filesystem or egress; foothold-scoped SSH forwards; durable cross-process step, time, token, and cost budgets; and per-arena plus system-wide stop that drains work predictably.

D1–D4 Planned

Discovery lane · vulnerability research

The offensive half the engine is missing. Patch-diff and variant hunting: ingest a vulnerable release and its fix, make the security-relevant difference a first-class hashed object, and sweep for the same defect where the fix did not reach. A fuzzing and triage path that finally feeds the crash oracle, with corpora as versioned artifacts, campaigns inside the confined-execution boundary, and automatic minimization and deterministic reproduction. Binary, appliance, and VM intake — promoted out of the deferred list, because the products worth researching are largely appliances, not source-available web apps. And campaigns: one product worked across months, findings deduplicated across sessions and versions, tracked to a disclosure bundle whose every claim resolves to a recorded identity.

E1–E5 Planned

Agent evaluation workbench

Durable records for agent builds, suites, evaluations, runs, and trials, plus generic drivers for interactive, containerized, and webhook-shaped agents. From the browser an operator selects a baseline and a candidate build, runs them over a held-out suite for repeated trials, and gets paired comparisons of verified capability, regressions, detection latency, cost, and safety — with active challenges that stage releases so reactive agents can be measured, not only one-shot exploits.

P1 Planned

Held-out flagship proof

Two artifacts, not interchangeable. First, a real vulnerability found and proven end to end on the platform — immutable identity, contained arena, observed effect, reproducible PoC, disclosure bundle — which does not wait on the evaluation workbench. Then a reproducible comparison between two agent versions over a held-out set built from confirmed findings with their truth withheld, published with its leakage policy, disclosed scaffolding, repeated-trial methodology, and stated uncertainty.

Deferred Out of scope for now

Product and multi-tenant concerns

MCP OAuth 2.1 and third-party tool-supply-chain defense, multi-tenant workspaces with SSO and graduated RBAC, live cloud and VM providers, multi-agent red-versus-blue, in-browser VNC, and public leaderboards. None are needed for a single-team, self-hosted evaluation product; they return only for a concrete need.
